# Research: how Knock would deliver refund Notifications in Cadence

Ticket: [#6](https://github.com/MarkOel3/cohort-005-project/issues/6). Map: [#1](https://github.com/MarkOel3/cohort-005-project/issues/1). Related: [#3 freshness research](https://github.com/MarkOel3/cohort-005-project/blob/research/notification-freshness/docs/research/notification-freshness.md), [#4 freshness decision](https://github.com/MarkOel3/cohort-005-project/issues/4), [#5 UI prototype](https://github.com/MarkOel3/cohort-005-project/issues/5).

**Question.** Does Knock fit Cadence's in-app refund Notifications, and how would it work here? There are two events. *Refund Request raised* goes to every Platform Admin (Instructor optional). *Refund Request approved / declined* goes to the buyer, who is a Student or a Team Admin.

This note sets out facts and trade-offs. The team makes the design decisions. There is no Knock account, so everything comes from Knock's docs (`docs.knock.app`, read in their `.md` form; see the index at `https://docs.knock.app/llms.txt`), Knock's OpenAPI spec (`https://docs.knock.app/openapi.json`), and the published npm packages, read as of 2026-11-15: `@knocklabs/react` 0.15.1, `@knocklabs/react-core` 0.17.1, `@knocklabs/client` 0.23.1 and `@knocklabs/node` 1.41.1.

## TL;DR

- **The fit is good overall.** Knock stores one in-app Message per recipient and gives each its own seen / read / archived state. A managed WebSocket pushes new Messages to the browser. `@knocklabs/react` provides a bell, a popover and a feed, or hooks if you want your own UI. `@knocklabs/node` triggers a workflow from a route action with one call.
- **Real-time comes from Knock, not from Cadence's server.** The browser opens a WebSocket (the Phoenix protocol) straight to Knock. Cadence's `react-router-serve` process needs no SSE, no custom server and no change-notify mechanism for SQLite. This removes most of the constraints in the #3 research, but only for the feed itself.
- **Seen state is always per recipient.** Knock cannot give an object (such as "Platform Admins") an in-app feed; that is on Knock's roadmap. So if one Platform Admin sees or reads a "Refund Request raised" Notification, it stays unseen for the other Platform Admins. A shared state would need Cadence to act, for example a bulk archive by `trigger_data` once the Refund Request is decided.
- **Sent feed Messages cannot be edited.** You can only change their status. To mark one stale ("already decided by someone else") you archive it and send a new one.
- **Groups.** Either list every Platform Admin's id in the trigger (up to 1,000 recipients per call), or use an Object plus Subscriptions and keep the subscriber list in sync with `users.role`. Audiences do not fit: an audience-triggered workflow only runs when a user *joins* the audience.
- **Auth.** In development the public key alone can act as *any* user. Before real users see it, turn on enhanced security mode and send a signed user token (an RS256 JWT, made with `signUserToken` from `@knocklabs/node`, no network call needed). Cadence's user ids are integers, so they must be sent as strings.
- **Free plan.** Up to 10,000 Messages a month, no hard cap, unlimited environments, unlimited feed retention, 30-day log retention. The pre-built feed shows **"Powered by Knock"** on plans that require branding; removing it is a paid feature.
- **Local dev and tests.** There is no Knock emulator, and the in-app channel **has no sandbox mode**. You can test without network calls because the Node SDK accepts a custom `fetch` and `baseURL`, and `KnockProvider` has `enabled={false}`. Workflow content (templates, steps) lives in Knock's dashboard unless the team manages it as files with the Knock CLI.
- **Possible poor fits:** per-recipient-only state (above); content can't be updated after sending; no event over the socket when *another* user changes state; Knock and SQLite can't share a transaction (a trigger can fail after the Refund Request row is written); a third party holds user ids, names and refund data; free-plan branding; workflows defined outside the repo.

## 2. In-app feed channel and real-time behaviour

- **Messages.** "A Message in Knock represents a notification delivered to a User or an Object on a particular channel." A workflow fans out to one *recipient workflow run* per recipient, and each run produces its own Message. ([Messages](https://docs.knock.app/concepts/messages), [Workflows: workflow runs and recipients](https://docs.knock.app/concepts/workflows))
- **Feed API.** `GET /v1/users/:id/feeds/:channel_id` returns `FeedItem`s in reverse chronological order (default `page_size` 50). Each item carries `data` (the trigger payload), rendered `blocks`, `actors`, `seen_at`, `read_at`, `archived_at` and `inserted_at`. With the response come `unseen_count`, `unread_count` and `total_count`. You can filter by `status`, `archived`, `source` (workflow key), `tenant`, `trigger_data` and `inserted_at.*`. ([In-app API](https://docs.knock.app/in-app-ui/api-overview); OpenAPI `/v1/users/{user_id}/feeds/{id}`)
- **Real-time.** "Knock provides a real-time web socket connection for your users to subscribe to new messages." The only event listed is `new-message`. It "will not contain the full message contents, but will include metadata about the updated badge counts. Might be throttled." The SDK then fetches the new items. ([In-app API: real-time delivery](https://docs.knock.app/in-app-ui/api-overview#real-time-delivery))
  - The socket is a managed service: "The socket connection is automatically managed by our SDKs, handling connection lifecycle, reconnection logic". The options are auto-disconnect for inactive tabs (`auto_manage_socket_connection`, default delay 2000 ms) and `__experimentalCrossBrowserUpdates`, which uses `BroadcastChannel` to keep tabs in sync. ([Socket behavior](https://docs.knock.app/in-app-ui/feeds/socket-behavior), [React Feed: socket options](https://docs.knock.app/in-app-ui/react/feed#socket-behavior-options))
  - In source, `@knocklabs/client` uses `phoenix` 1.8.9's `Socket`. It opens the socket only when `typeof window !== "undefined" && typeof WebSocket !== "undefined"`, and disconnects on `visibilitychange` / reconnects on `online` (`dist/esm/api.mjs`, `pageVisibility.mjs`).
  - **No event is documented for status changes made elsewhere**, such as another Platform Admin reading their own copy, or a server-side archive. A feed that is already open learns about those on its next fetch, or through the experimental cross-tab sync for the *same* user. This is an inference from the event list above.
- **Archiving.** Archived Messages are excluded from the feed by default (`archived: only` / `include` brings them back). The pre-built feed archives when you click "x". ([In-app feeds: archiving](https://docs.knock.app/integrations/in-app/feeds#archiving-messages))
- **Immutability.** "Can I update a feed message after it's been sent? No. You can update a feed message's engagement statuses … but its content and other metadata can't be changed … If a message becomes out of date, archive it and trigger the workflow again to send a new one." ([In-app feeds FAQ](https://docs.knock.app/integrations/in-app/feeds#frequently-asked-questions))
- **Template.** The in-app step's template is edited in Knock's template editor (Liquid). Its variants are Standard (the whole cell is clickable, with an optional action URL), Single-action and Multi-action (buttons). The action URL can be dynamic, e.g. `{{ data.url }}`. ([In-app feeds](https://docs.knock.app/integrations/in-app/feeds#action-url))
- **Retention.** "In-app feed notifications are available indefinitely" even after message *logs* expire (30 days on non-Enterprise plans). Custom retention policies are "not currently supported". The pricing page lists feed retention as "Unlimited … can be configured". ([Data retention](https://docs.knock.app/manage-your-account/data-retention), [pricing](https://knock.app/pricing)) This bears on the map's "Retention" item: by default Knock keeps everything, and hiding old items is up to the UI (filters such as `inserted_at.gte`) or archiving.

## 3. React SDK and fit with React Router v8 / SSR

- **Packages.** `@knocklabs/react` (UI) sits on `@knocklabs/react-core` (hooks, built on `swr` and `@tanstack/react-store`) and `@knocklabs/client` (API + socket). React peer is `^17 || ^18 || ^19`, so it fits Cadence's React 19.2. The peers `next` and `@tanstack/react-router` are **optional** (`peerDependenciesMeta`) and used only by the `/next` and `/tanstack` entry points (guide location sensors). There is no React Router entry point and none is needed for feeds. (npm metadata; package `exports`)
- **Components.** `KnockProvider` (`apiKey`, `user`, `userToken`, `onUserTokenExpiring`, `host`, `enabled`) → `KnockFeedProvider` (`feedId`, `defaultFeedOptions`, `colorMode`) → `NotificationIconButton` (badge `unseen` by default, `badgeCountType="unread"` optional), `NotificationFeedPopover`, `NotificationFeed`. You can override `renderItem` and `onNotificationClick` / `onNotificationButtonClick`. Styling uses `--rnf-*` CSS variables or full replacement of the `rnf-` classes, and needs `import "@knocklabs/react/dist/index.css"`. Headless use is possible through hooks (`useKnockFeed`, `useNotifications`, `useNotificationStore`). ([React overview](https://docs.knock.app/in-app-ui/react/overview), [Feed](https://docs.knock.app/in-app-ui/react/feed), [Custom UI](https://docs.knock.app/in-app-ui/feeds/custom-ui))
- **Default seen/read behaviour of the pre-built feed:** opening the popover marks everything **seen**. Clicking an item marks it **read** and follows its action URL. "Mark all as read" exists. ([Feed: mark-as-read](https://docs.knock.app/in-app-ui/react/feed#mark-as-read-behavior), [In-app feeds: statuses](https://docs.knock.app/integrations/in-app/feeds#how-the-knock-in-app-feed-uses-status))
- **Links in an SPA.** The default click redirects the browser to `action_url` (a full page load). To use client-side navigation you would pass `onNotificationClick` and call React Router's `navigate`. ([Handling interactivity](https://docs.knock.app/in-app-ui/feeds/handling-interactivity))
- **Toasts.** Knock's toast recipe listens on the feed client (`useKnockFeed().feedClient`) for real-time items and uses `react-hot-toast`. Cadence's existing `sonner` could take the same listener. That is an inference; the docs only show `react-hot-toast`. ([Toasts](https://docs.knock.app/in-app-ui/react/toasts))
- **SSR (from source; not run).** Both ESM entry points start with `"use client"`, which only matters under React Server Components. In the source, `useNotifications` creates the feed client during render, the socket is guarded by `typeof window`, and the feed data is fetched on the client after mount. So the server-rendered HTML would contain an empty or loading feed and badge, and the data would arrive after hydration. The docs say nothing about SSR, pre-fetching or passing a server-fetched feed into the components. If the badge must be in the first HTML, Cadence would need its own server-side call to the feed API, or a count stored in Cadence. `enabled={false}` "render[s] children but keep[s] the Knock client idle: no identify call, no API requests, and no websocket", which helps when the user token or the user is not ready (`KnockProvider.d.ts`). *I could not run an SSR smoke test in this environment, so treat SSR behaviour as unverified.*
- **Env vars on the client.** The browser needs the public key and the feed channel id. In Vite these are `VITE_*` variables, or the root loader can pass them down. The secret key and signing key must stay on the server. ([React quick start](https://docs.knock.app/getting-started/quick-start/react))
- **Dependency weight.** `@knocklabs/react` brings `@telegraph/*` (Knock's design system), `@radix-ui/react-dialog` / `hover-card`, `@popperjs/core` and its own `lucide-react` `^0.544`, a different minor from Cadence's `^0.563`. This may duplicate `lucide-react` in the bundle. (npm metadata)
- **Branding.** In source, `NotificationFeed` renders a "Powered by Knock" footer when the feed settings return `features.branding_required` (`dist/esm/modules/feed/components/NotificationFeed/NotificationFeed.mjs`). The pricing page lists "Removing Knock branding" as not included on Free. A headless UI built from hooks does not render that footer, though the plan's terms may still apply.

## 4. Recipients and authentication

- **Identifying users.** A user must exist in Knock before it can receive a Notification. All identification is an upsert. It can be *direct* (`PUT /v1/users/:id`), *inline* (pass `{ id, name, … }` objects in the trigger's `recipients` or `actor`), *bulk* (up to 1,000 per call), or client-side, where `KnockProvider` upserts the `user` it is given when it mounts. Knock recommends "using your internal user identifier for the `id`". Ids are strings, so Cadence's integer `users.id` would be sent as e.g. `"42"`. ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients))
- **Mapping Cadence people.** Knock has no notion of roles. Platform Admin, Team Admin, Student and Instructor are all Knock *users*. Role only matters when Cadence picks the recipients, or as a custom property if the team wants Knock conditions to use it. (Inference from the recipients docs.)
- **Keys.** The backend uses a secret key (`KNOCK_API_KEY`, the Node SDK's default env var). The browser uses a public key. Each environment has its own keys. ([Security](https://docs.knock.app/in-app-ui/security-and-authentication), [Environments](https://docs.knock.app/version-control/environments))
- **Without enhanced security (the default):** "a request with your public key can act as any user." Endpoints open to the public key include reading any user's feed, marking messages, and `PUT /v1/users/:id`. Since Cadence's ids are small sequential integers, guessing them is trivial. ([Security](https://docs.knock.app/in-app-ui/security-and-authentication#authentication-without-enhanced-security))
- **With enhanced security mode:** Knock rejects public-key requests that lack a signed user token. The token is an RS256 JWT with `sub` = user id (`iat` / `exp` recommended), signed with the environment's signing key (`KNOCK_SIGNING_KEY`). `signUserToken(userId, { expiresInSeconds = 3600, grants, signingKey })` from `@knocklabs/node` does this locally ("without an additional network request"). Grants can limit a token to e.g. `user/feed_read` + `user/feed_write` with `explicit_grants: true`. Knock suggests matching the token's expiry to the session's, or refreshing through `onUserTokenExpiring`. Calling `authenticate` again restarts the socket. In Cadence the token could be signed in the root/app loader from `getCurrentUserId` and passed to `KnockProvider`. (Docs; `lib/tokenSigner.d.ts`)
- **Dev user switching.** `KnockFeedProvider` is keyed by `userId` + feed id (`KnockFeedProvider.mjs`), so switching users in the DevUI panel remounts the feed for the new user, provided the token changes with it.
- **Rate limits** are per environment, or per environment **and** signing user when a user token is used. Trigger is tier 5 (1,000 req/s). ([Rate limits](https://docs.knock.app/api-reference/overview/rate-limits); OpenAPI `x-ratelimit-tier`)

## 5. Server-side triggering from Node

- **Call.** `new Knock()` (reads `KNOCK_API_KEY`), then `await knock.workflows.trigger("refund-request-raised", { recipients, actor, data, tenant?, cancellation_key? })`. It returns `{ workflow_run_id }`, and "all workflow runs are executed asynchronously". `data` can be up to 10 MB. `recipients` is "Limited to 1,000 recipients" and accepts ids, inline user objects or object references. (OpenAPI `TriggerWorkflowRequest`; `resources/workflows.d.ts`)
- **SDK.** `@knocklabs/node` 1.x is generated by Stainless. It needs Node 20 LTS or later and uses the global `fetch`. It retries connection errors, 408, 409, 429 and 5xx twice by default (`maxRetries`) and times out after 1 minute by default (`timeout`). Its only runtime dependency is `jose` (ESM-only; the README has a CJS workaround, which Cadence does not need because it is `"type": "module"`). (README, `client.d.ts`)
- **Idempotency.** `POST /workflows/:key/trigger` is the only endpoint that accepts `Idempotency-Key`. The window is 24 h and only 2xx responses are cached. The docs suggest keys like `order-placed:user-123:order-456`; for Cadence that could be `refund-request-raised:<refundRequestId>`. The SDK also sets a default idempotency key on its own retries. ([Idempotent requests](https://docs.knock.app/api-reference/overview/idempotent-requests); `client.js`)
- **Where it would go.** After `raiseRefundRequest` succeeds in `courses.$slug.refund.ts`, and after `approveRefundRequest` / `declineRefundRequest` succeed in `admin.refunds.tsx`. SQLite and Knock can't share a transaction. If the trigger fails or times out after the row is written, the Refund Request exists with no Notification. Whether to await the trigger, fire and forget, or record pending triggers in SQLite (an outbox) is a design choice. Awaiting adds Knock's latency (and up to 2 retries) to the action's response.
- **What to pass.** `data` reaches the feed item unchanged ("all of the `data` in the workflow run scope will be included"), unless an API response filter removes keys. This is how ids like `refundRequestId`, a course slug or a URL reach the UI and the template. The `actor` (e.g. the buyer, or the deciding Platform Admin) is shown as the cell avatar/name. Keep in mind that by default the feed API returns the actor's custom properties, the whole trigger data, and the recipient's properties to the browser; the response filter trims these. ([In-app API: passing through data](https://docs.knock.app/in-app-ui/api-overview#passing-through-data), [Customizing API response](https://docs.knock.app/integrations/in-app/feeds#customizing-api-response-content))
- **Workflow definitions** (steps, in-app template, action URL) live in Knock. You build them in the dashboard, or pull and push them as local files with the Knock CLI (`npm i -g @knocklabs/cli`). API triggers use the last **committed** version. ([CLI](https://docs.knock.app/cli/overview), [Testing workflows](https://docs.knock.app/send-notifications/testing-workflows))

## 6. Sending to "all Platform Admins"

| Option | How | Trade-offs |
| --- | --- | --- |
| **List recipients in the trigger** | Query `users` where `role = 'admin'`, pass their ids (optionally inline-identified) | Cadence's DB stays the source of truth; up to 1,000 per call; one query per raise |
| **Object + Subscriptions** | Identify an object, e.g. collection `roles` / id `platform-admins`; `objects.addSubscriptions` for each Platform Admin (100 per call, no total limit); trigger with `recipients: [{ collection, id }]` | Knock fans out and deduplicates; the trigger doesn't need a DB query; but subscriptions must be kept in sync whenever `users.role` changes (and in seeds). The object itself also gets a workflow run, but objects can't have an in-app feed ("Objects API support for in-app feed notifications" is on the roadmap) |
| **Audiences** | Dynamic/static user segments | Not suitable: "workflows trigger only for **new users** who join an audience", so you can't target the whole audience per event |

Sources: [Subscriptions](https://docs.knock.app/concepts/subscriptions), [Objects](https://docs.knock.app/concepts/objects), [Audience triggers](https://docs.knock.app/send-notifications/triggering-workflows/audiences).

**Instructor (optional).** Add the course's Instructor id to the same `recipients` list, or trigger a second workflow for them. Knock deduplicates recipients within one fan-out. ([Subscriptions: deduplication](https://docs.knock.app/concepts/subscriptions#deduplication-by-default))

**Buyer for approved / declined.** This is a single recipient: the purchase's `userId`, whether a Student or a Team Admin.

## 7. Seen / read / archived state

- **Engagement statuses:** `unseen` → `seen` (rendered in the feed) → `read` (marked read), and separately `archived`, `interacted` and `link_clicked`. A Message can carry several engagement statuses at once. Clients can set and unset `seen` / `read` / `archived` per Message (`PUT` / `DELETE /v1/messages/:id/:status`) or in batches (`POST /v1/messages/batch/:status`). ([Message statuses](https://docs.knock.app/send-notifications/message-statuses), [Security: endpoint table](https://docs.knock.app/in-app-ui/security-and-authentication))
- **Per recipient only.** Each Platform Admin has their own Message, with its own status. Objects can't receive feed Messages (see §6). So "seen by one Platform Admin = seen by all" is **not** built in.
- **What the server can do.** `POST /v1/channels/:channel_id/messages/bulk/:action` (`archive`, `read`, `seen`, …) accepts filters including `recipient_ids`, `workflows`, `trigger_data` and `engagement_status`. With this Cadence could, for example, archive or mark read every "raised" Message for `refundRequestId = 42` when it is decided. (OpenAPI) It is an asynchronous API call, and the socket sends no event for it (§2), so other open feeds would only change on their next fetch.
- **Staleness (map item).** Since content can't be updated, a decided Refund Request's "raised" Notification either stays as it was, gets archived (bulk, as above), or is archived and replaced by a new Message. The UI could also look up the current status from Cadence when it renders, using the `refundRequestId` in `data`.

## 8. Free plan limits

From [knock.app/pricing](https://knock.app/pricing) and [Knock plans](https://docs.knock.app/manage-your-account/knock-plans). Note the "Developer plan" has been renamed the **Free** plan.

- 10,000 Messages / month. "A message is counted each time a notification is successfully delivered to a single user on a single channel," so a "raised" event with 3 Platform Admins counts as 3. There is no hard cap: if you go over without a billing method, Knock contacts you.
- Unlimited environments and team seats; 99.9% uptime SLA listed; 30-day log retention; feed retention unlimited.
- Not on Free: removing Knock branding, translations, custom roles, audit logs, SSO, per-tenant branding and preferences, and others. Batch render limits above 10 items are Enterprise-only.
- Starter is $250 / month for 50,000 Messages.
- **Usage accrues in every environment, including development.** The in-app channel has no sandbox mode: "The in-app channel doesn't support sandbox mode … Use channel conditions." So dev and test triggers against Knock count toward the 10,000.
- EU data residency is "expected … by the end of 2026" and is not available yet.

## 9. Local dev and testing without network calls

- **Knock environments.** An account starts with production only. "Enable environments" adds development, which has separate keys and data, and content is then promoted. Enhanced security mode can stay off in development. ([Environments](https://docs.knock.app/version-control/environments))
- **Dashboard testing.** The workflow test runner offers a "Sandbox mode" setting and "Skip delays". The API offers `settings.sandbox_mode`, but this does not apply to in-app delivery (§8). ([Testing workflows](https://docs.knock.app/send-notifications/testing-workflows))
- **No emulator.** The docs describe no local Knock server and no mocking guide.
- **Server tests without network.** `new Knock({ apiKey, baseURL, fetch })` accepts a custom `fetch` and `baseURL` (env `KNOCK_BASE_URL`), so a Vitest test can pass a stub `fetch` and assert on the trigger body. A thin module wrapping the trigger calls could also be replaced in tests. (`client.d.ts`) `signUserToken` runs locally with a test RSA key.
- **Client.** `KnockProvider` accepts `host` (point at a stub server) and `enabled={false}` (no API calls and no socket), so component tests and SSR can run offline. (`KnockProvider.d.ts`)
- **Keys in `.env`.** The secret key, public key, feed channel id and signing key. The public key and channel id must reach the browser (§3).

## 10. Things that may make Knock a poor fit

1. **State is per recipient only.** A Platform Admin group can't share one seen/read state, and objects can't have feeds. Shared state means Cadence calls the bulk-status API.
2. **Messages are immutable.** Staleness after a decision means archiving and re-sending, or rendering the live status from Cadence.
3. **The socket carries only `new-message`.** Archive or read changes made elsewhere (another tab, another admin, the server) are not pushed. Cross-tab sync for the same user is experimental.
4. **No shared transaction with SQLite.** A trigger can fail after the row is written; reliability is up to Cadence.
5. **SSR gives an empty feed or badge in the first HTML.** There is no documented server pre-fetch for the components.
6. **Data leaves Cadence.** User ids, names, refund reasons and anything else in `data` or `actor` are stored by a US-hosted third party (EU residency not yet available), and by default the feed API returns `data` and `actor` properties to the browser.
7. **Free plan.** Branding on the pre-built feed; dev and test usage counts, since in-app can't be sandboxed.
8. **Configuration outside the repo.** Workflows and templates live in Knock unless the team adopts the CLI. Tests can't exercise the real template rendering offline.
9. **Security defaults to open.** Enhanced security mode plus user tokens are needed before launch, given guessable integer ids.

## Implications for other tickets

- **#4 (freshness decision).** If Knock delivers the feed, the live part is Knock's WebSocket, and none of #3's options 3 and 4 (SSE, custom WebSocket server) are needed *for the feed*. Two things remain in Cadence: keeping Cadence's own pages (e.g. the `admin.refunds` list) fresh when another Platform Admin decides, and the fact that status changes are not pushed.
- **#5 (UI prototype).** The pre-built bell, popover and feed fix some behaviour: seen on open, read on click, unseen-count badge, "x" archives, "Powered by Knock" on Free. A custom UI through hooks avoids those, but means building it. Click handling needs `onNotificationClick` + `navigate` to avoid full page loads.
- **Map "Not yet specified":**
  - *Data model:* Knock already stores one Message per recipient. Cadence may not need its own Notification table, but it would hold no record of what was sent unless it keeps one.
  - *Seen shared vs per Platform Admin:* Knock gives per-admin state; shared state needs extra work (§7).
  - *Staleness:* constrained by immutability (§2, §7).
  - *Retention:* Knock keeps feed items indefinitely by default.
  - *Linking:* through the template's action URL or `data` plus `onNotificationClick`. Knock does no access checks on that URL.
